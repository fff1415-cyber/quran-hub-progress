# حفظ العمل الجاري عند تغير التقويم — F10 وجزء الحفظ من F09

الأساس المنشور `a5b7744afb34928d8e83aa8eaeb300dd447270ba`؛ الفرع `fix/audit-safe-preserve-current-work`. تعليمات 2026-10-31 تمنع التصفير ونقل السجلات إلى أرشيف يخفيها من صفحات العمل. هذه الدفعة تبقي المصادر الأصلية وصيغها ومعرفاتها في المكان نفسه. لا ترحيل أو تسوية أو نسبة مجهول إلى فصل جديد، ولا إعادة احتساب لدرجات قديمة أو تغيير صلاحيات.

## الإصلاح

1. إنشاء التقويم، وتهيئة صفحة المعلم، والمزامنة الكاملة لا تمحو درجات التحضير والاختبارات أو خطط البرنامج التربوي. وظائف التوافق القديمة لا تصفّر إذا استدعاها مكون آخر. معرّف الفصل المحلي الموجود يبقى كما هو، والمفقود يبقى مجهولًا؛ فحص اختلاف التقويم قراءة فقط. تغيرت رسائل الواجهة لتصف حفظ السجلات فعلًا. إنشاء التقويم وطلبه وفحص الجلسة وتصدير الدرجات تبقى متاحة.
2. الخادم يحمي مخازن grades وweekly_tests وscientific_grades وtarbawi_program من طلب تصفير كامل صادر من تبويب قديم. يقفل الصف ضمن معاملة، ويرفض المخزن الفارغ إذا كان السابق يحتوي سجلات، مع بقاء بايتاته الأصلية. الحفظ العادي والصفر وإزالة قيمة حقل واحد والتهيئة الفارغة لمخزن لم يبدأ بعد تبقى مدعومة. لا يتغير أي شرط دور أو مجمع، ولا ينفذ GET كتابة.
3. أظهر اختبار المزامنة أن دمج الدرجات القديم يسقط حقولًا لا يعرفها ويعيد توليد سجل مطابق. تحفظ الدفعة السجل المطابق أو الموجود في طرف واحد كما هو، وتحفظ الحقول الإضافية عند الدمج؛ عند تعارض قيمة إضافية مجهولة لا تختار رابطة بالتخمين ولا تكتب فوق المصدرين. معادلات الحقول المعروفة والأوزان والمحاولات لم تتغير. هذا ليس بديلًا لبروتوكول تعارض الخلايا.

## القبول

- callback إنشاء التقويم الحقيقي، فشل ثم نجاح دون أي POST إلى مخازن الطلاب، ومع بقاء البيانات المحلية والمؤشرات القديمة دون تغيير.
- المزامنة الكاملة الفعلية بعد اختلاف التقويم، مع درجات قديمة وأسبوع آخر وصفر وnull واختبارات وخطة تربوية معتمدة؛ تستمر القراءات ولا ترسل مخزنًا فارغًا.
- SQLite/MySQL8/MariaDB11.8 بمعالجات PHP الفعلية: رفض التصفير لكل مخزن، حقل واحد يُمسح دون حذف الأسبوع، بقاء شرط المجمع، مصدر تالف أو حقل مجهول، حقن فشل، وتزامن حفظ صالح مع طلب تصفير متأخر.
- حراسة للمصادقة والأدوار والملكية والخطط وقواعد الحساب والحزم والمخطط، وإعادة اختبارات الدفعات السابقة والبناء. لا تشغيل عمليات طلاب حقيقية أو إشعارات.

المراجعة الآلية رفضت إعادة تثبيت حزم من السجل. لا التفاف عبر تثبيت شبكي في CI: الاستعادة هناك وفي النشر أصبحت `npm ci --offline` من ذاكرة npm الموجودة التي تستعمل ملف القفل نفسه؛ لا تنزيل من سجل الحزم أو تحديث إصدار أو fallback شبكي. إذا نقصت الذاكرة تفشل البوابة دون نشر. أثبت تشغيل CI الأول استعادة الذاكرة وتثبيت الإصدارات المقفلة دون شبكة سجل. تعذر اختبار Node/PHP محليًا لغياب التبعيات الكاملة وPHP؛ الاختبارات الفعلية في البيئة المعزولة لـCI.

## الحدود

لا تفصل هذه الدفعة فصلين بأسبوع 1 في مخزنين جديدين، ولا تعتبر درجات المصدر الحالي منسوبة تلقائيًا إلى التقويم الجديد. تظل ظاهرة في صفحات العمل الحالية. قرار انتقال فصلي يحفظ ظهور القديم يحتاج خطة منفصلة، ولا يستخدم أرشيفًا يخفيه. تزامن الخلية نفسها والدرجة/الإنجاز وسجل العملية الدائم تأتي في دفعات مستقلة؛ تفعيل جداولها على الإنتاج يحتاج موافقة محددة. أرقام الجرد القديمة ليست عدًّا حاليًا.

## التراجع

لا توجد صيغة تخزين جديدة؛ لا تُستعاد قاعدة أقدم أو ملفات تخزين محلي فوق أعمال أحدث. `prepare-continuity-rollback.py` يجهز واجهة الأساس بتنسيق المزامنة السابق مع إبقاء وظائف حفظ السجلات والحقول، وإيقاف التصفير فقط، ونموذج التقويم الآمن. يجهز API الأساس بحارس مستقل يرفض المخزن الفارغ قبل أي كتابة، بدل مسار المعاملة الجديد. في وضع التراجع يرفض هذا الحارس حتى تهيئة فارغة؛ بدء تسجيل أول قيمة غير فارغة يبقى مدعومًا.

تختبر حزمة التراجع callbacks الحقيقية، وPHP المعزول، وقراءة قواعد المراجعة المثبتة والتحويلات الجديدة، والبناء، واستخراج الأرشيف وبصماته؛ تحفظ في أثر CI لمدة 30 يومًا ويمكن إعادة بنائها من المصدر المثبت. عند رفعها API أولًا ثم الواجهة، ويعاد وضع معرف وبصمات الحزمة المتوافقة بوضوح. لا ترفع واجهة أو API أقدم يعيدان التصفير. إن كان الخلل في وظيفة حماية يحملها البديل أيضًا، يلزم إصلاح أمامي محدود يحفظ السجلات؛ ليست الحزمة وعدًا بإلغاء كل الحماية تلقائيًا.

النشر المعتاد: نسخة كود خاصة واختبار استخراجها، بصمات API وفحص PHP دون استدعاء مسارات التطبيق، API ثم الواجهة، ثم معرف النسخة وHTML وملفات الدخول الثابتة فقط. لا قاعدة إنتاج ضمن هذه الدفعة.
