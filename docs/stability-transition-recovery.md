# Complete passing-assessment recovery

Depends on the unmerged shared-transfer branch (#59), itself based on #58 and #56. Keep the complete application stack; the separate hosting probe #57 is not an application dependency. No production deployment or merge is authorized until the real restore, current backup, domain isolation and acceptance gates are satisfied.

The full and review-only passing callbacks retain raw errors/warnings, assessed zero, the adopted evaluation-rule snapshot and source queue/assignment identity. Before the first network request, an account/tenant-scoped durable intent freezes the complete assessment and plan date. The serialized transition is then stored in a separate immutable per-operation entry before sending. Quota failures prevent a new request. Reopening the browser and root-level recovery reuse the original intent/request; unresolved or differing assessments are shown explicitly and never replaced by a guessed result.

The authenticated read-only `/plans/capabilities` endpoint lives in the same PHP file as the assignment handler. A new client requires protocol 2 and all three capabilities before sending a complete transition; old or mixed backend versions cannot silently accept a partial transition. Existing manual assignment and legacy protocol paths retain their behavior.

The existing assignment transaction now commits the detailed assessment, academic record, queue pass, assignment/profile and immutable receipt together. Readiness, due date (server clock), source assignment, completed hifz and catalog successor are validated server-side. Failed late SQL writes roll the entire transaction back. All old history rows are retained without truncation or regrading; generic history saves cannot alter confirmed records. Native MySQL/MariaDB acceptance exercises simultaneous identical recovery and late history/receipt failures.

Receipt recovery reads current queue, student profile and plan sheet; it never overlays a historical queue/profile snapshot from a receipt. A later plan is marked for historical review rather than regressed. Both passing UIs wait for confirmation and avoid legacy echo writes, duplicate notifications and a redundant network flush after confirmed success.

The actual catalog terminal plan can be finalized atomically while keeping its existing active assignment visible. No successor assignment or new educational/graduation policy is invented. Legacy entries without a provable source assignment are blocked for review and are not attributed to the current plan by guessing.

Acceptance uses synthetic local/CI databases only: `transition-history.php`, `transition-recovery-sessions.cjs` (actual client serializer and production router), `transition-ui.cjs` (actual callbacks), existing affected assignment/academic and failure/deferral tests, and `transition-native.php` for MySQL 8/MariaDB 11.8. This does not prove connectivity or restore integrity on Hostinger. Failed assessment/deferral remains the existing separate queue/history workflow and is not claimed to have this new atomic passing protocol. No production migration or runtime flag was activated.
